# 发布前检查（Preflight）

## 目的

把「能发布了吗」这个凭感觉的问题，变成**8 项能逐条验过、每项都带实测值**的核对表。

只查**发布底线**：公网能不能打开、跑的是不是最新代码、有没有把不该带的东西带上去。
不查功能对不对（那是各自的 `check-dayN.js`），也不查好不好看（那是 `web-frontend-audit`）。

## 为什么要有这个检查

因为**"看起来没问题"和"真的没问题"之间，隔着一整类沉默的故障**：

| 你以为 | 实际可能是 | 谁会先发现 |
|---|---|---|
| 页面能打开 = 部署成功了 | 打开的是**三天前的旧版** | 用户 |
| 接口 200 = 一切正常 | 前端压根没连上这个接口 | 用户 |
| 本地测过了 = 线上也对 | **改了但忘了部署** | 用户 |
| 密钥在 `.gitignore` 里 | 从不检查"实际有没有被跟踪" | 全网（爬虫） |

**这类问题的共同点：不报错、不弹窗、控制台干净。**
它们只在「我以为我改好了」和「用户实际看到的」之间撕开一道缝 —— 而且**总是别人先发现**。

## 8 项检查（`bash scripts/preflight.sh` 逐条跑）

### 【1】公网页面能打开
- [ ] HTTP 状态 **200**
- [ ] 返回体**不是空的**（记录字节数）
- [ ] 含 `<title>`（能看出是个真页面）

**不合格的典型**：404 / 空响应 / 拿到一个错误页

### 【2】打开的是应用、不是中间页
- [ ] 内容含应用特征词（本产品：`这一周`）
- [ ] **不含**腾讯云的 `页面访问提示`

**为什么单列一项**：腾讯云默认域名会插一个强制提示页。
**HTTP 200 也能是这个提示页** —— 只看状态码会把它当成部署成功。
（这是本产品 Day 21 验收里如实标 FAIL 的那一条，官方写明关不掉。）

### 【3】接口活着
- [ ] `GET /api/courses` → **200** + `ok: true`
- [ ] 顺手记下条数（能看出数据还在）

### 【4】线上前端 == 本地前端 ⭐ **最容易漏的一项**

逐文件比对 `index.html` / `app.js` / `store.js` / `mock-data.js` /
`manifest.json` / 三个 icon（文本比内容、图片比 sha256）。

**为什么要专门查**：
- 页面**照样能打开**（第 1 项绿）
- 接口**照样是通的**（第 3 项绿）
- 密钥**照样干净**（第 5 项绿）
- **但用户看到的是旧界面**

这类问题**没有任何一项会红**，除非你专门比对 —— 所以它值得单独一项。

**不合格的典型**：改了代码 → 跑通了本地 → **忘了部署** → 一切看起来都好

⚠️ **误判提醒**：刚部署完 CDN 可能还没刷新（腾讯云官方说"usually in a few minutes"）。
**部署后等 1–2 分钟再跑本项**，否则会假红。

### 【5】仓库里没有密钥
- [ ] `python audit-secrets.py` → **0 命中**（工作区 + git 全历史）

**不合格的典型**：`.env` 被 `git add -f` 强加过一次 → `.gitignore` 形同虚设

### 【6】`.env` 被忽略
- [ ] `git check-ignore .env` **命中**（光看 `.gitignore` 里写了不算数 —— 要问 git 本人）

### 【7】工作区干净
- [ ] `git status --short` **为空**

**为什么要查**：有未提交的改动 = 线上跑的可能是"半成品"；
而且**你正在看的那份代码，不是仓库里的那份**。

### 【8】没有没推的提交
- [ ] 本地 `HEAD` == 远端 `origin/main`

**为什么要查**：提交了但没推 = 别人 clone 不到；
**"我明明提交了"和"远端真的有"是两件事**。

（本机网络常抖，`push` 可能静默失败 —— 这一项就是它的兜底。）

## 输出格式

每项**必须带实测值**，光一个 ✅ 不算证据：

```
【4】线上前端 == 本地前端
     ❌  不一致：app.js 本地 51988 字节 / 线上 51772 字节
         ↳ 多半是「改了但没部署」。跑：bash scripts/deploy-web.sh
```

结尾给一句**明确的结论**：

```
  8 项检查：7 通过 · 1 失败
  ❌ 有 1 项没过，先别发布。
```
或
```
  8 项检查：8 通过 · 0 失败
  ✅ 全绿，可以发布。
```

## 🔑 怎么证明这个检查不是摆设（本 Skill 的核心要求）

**跑通过 ≠ 检查有效。**

一个**永远输出 ✅** 的检查，和**真的全绿**，在屏幕上长得一模一样。
（本产品 Day 23 的实测教训：密钥扫描器第一次跑就发现 **8 条规则里有 3 条是坏的** ——
要不是先做了自检，那个"命中 0 条"就是假的安全感。）

所以有两条硬要求：

### 要求 1：每项输出必须带实测值
"✅ 密钥检查通过" **不算**证据。
"✅ `audit-secrets.py` → 0 命中（8 类规则 + git 全历史）" **才算** ——
因为它同时告诉了你"用的是什么尺子、量到多少"。

### 要求 2：定期**故意弄坏一项**，确认它真的会红

做完任何一次改动后，至少做一次：

1. **制造一个已知问题**（最方便的是改一行本地 `app.js` 但**不部署** → 第 4 项必红）
2. 跑检查 → **必须红**，而且红的那项要**指名道姓**说清哪里不一致
3. **把问题还原** → 再跑 → 必须恢复全绿

**如果第 2 步没红，那是个比原问题更严重的发现**：
说明这一项检查失效了，它给的一切 ✅ 都不可信。

> 一句话：**一个从来不报错的检查，等于没有检查，还会让人以为自己有检查。**

## 已知边界（不查）

| 不查 | 为什么 |
|---|---|
| 功能对不对（能不能存、能不能删） | 各有 `check-dayN.js`；本 Skill 只管"发布出去是什么样" |
| 视觉/可读性/触达尺寸 | 属 `web-frontend-audit` |
| 性能（首屏耗时、包体积） | 本产品是演示规模 |
| 手机真机上的表现 | 需要真机，自动化替代不了 |
| 刚部署完 1 分钟内的 CDN 延迟 | 会假红，见【4】的提醒 |
| 数据库内容对不对 | 只查"接口通不通"，不查数据对不对 |

## 怎么跑

```bash
cd my-first-site
bash scripts/preflight.sh
```

脚本退出码：`0` = 全绿可以发布；`1` = 有项没过。
（便于以后接流水线 —— 但**本期明确不做流水线**，先人工跑。）
