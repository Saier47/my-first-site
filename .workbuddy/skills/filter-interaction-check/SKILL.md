# 筛选 / 搜索交互的完整性检查

## 目的

把「这个搜索框好用吗」这种主观问题，变成**三种情况能不能逐一验过**的可核对事项。

只查**底线**：用户能不能分清"确实没找到"和"功能坏了"。不查上限（搜得准不准、排序合不合理）。

## 为什么专门查这件事

一个筛选功能有四种可见状态，其中**「无结果」最容易被漏掉**：

| 情况 | 用户看到的 | 用户以为的 |
|---|---|---|
| 有结果 | 筛出来的条目 | 正常 |
| **无结果** | **（一片空白）** | ⚠️ **"是不是卡了/坏了/我没搜上？"** |
| 清空输入 | 全部条目回来 | 正常（但如果没回来 = 坏了） |

**一片空白是"沉默的失败"** —— 它不报错、不弹窗、控制台干净，但用户已经开始怀疑自己了。

这和本产品 Day 11 学到的教训同源：**"没生效"和"还没生效"在用户眼里长得一样**；
这里是 **"没找到"和"坏了"在用户眼里长得一样**。
→ 无结果时必须有一句话**明确说明**"没找到 X"，而不是让用户对着空白猜。

## 检查清单（三种情况逐条验）

### 情况 ①：有结果

- [ ] 输入一个**确实存在**的关键词，结果区只出现匹配项
- [ ] **不匹配的项确实消失了**（不是"没变"——要能看出被筛掉了）
- [ ] 有**结果数量**的提示（如"找到 3 条"），让用户确信搜索生效了
- [ ] 大小时写无所谓（搜"高数"和"高數"能不能都中，属上限，不查）

**不合格的典型**：输入之后页面完全没变化（说明没绑定事件，或筛了但没重渲染）

### 情况 ②：无结果 ← **重点**

- [ ] 输入一个**绝对不存在**的关键词（如乱码 `zzzz`）
- [ ] **不能只是空白**，必须有一句明确文案
- [ ] 文案里**带上用户搜的词**（"没找到 zzzz"），证明系统读懂了输入
- [ ] 文案要**给出下一步**（"换个词试试"），而不是只报死讯
- [ ] 这个空状态和"数据本身为空"的空状态**要能区分**
      （"你还没添加任何课程" ≠ "没找到 zzzz"——两件事，别用同一句话）

**不合格的典型**：输入 `zzzz` → 页面一片空白 → 用户分不清是搜不到还是页面挂了

### 情况 ③：清空恢复

- [ ] 清空输入框 → **全部条目回来**
- [ ] 恢复后**数量与筛选前一致**（筛走的东西要一条不少地回来）
- [ ] 结果计数提示**消失或归位**（不能还显示"找到 0 条"）
- [ ] 无结果文案**消失**（不能留在页面上）

**不合格的典型**：清空后只回来一部分（说明筛选时**改了原数组**，不是筛选视图）

## 怎么判断"改没改原数组"（最常见的实现 bug）

筛选应该是**派生的视图**，不是**对原数据的修改**：

```js
// ❌ 会把原数组筛小，清空后回不来
all = all.filter(x => x.name.includes(q));

// ✅ 原数据不动，每次从 all 重新筛
const shown = all.filter(x => x.name.includes(q));
```

**验证方法**：连续操作 —— 搜 `a` → 清空 → 再搜 `b` → 清空。
如果第二次的结果比第一次少，就是原数据被改掉了。

## 检查的可达性要求（顺序不可颠倒）

1. **先确认页面上真的能找到一个筛选输入框**。
   找不到时**不要立刻说"功能缺失"** —— 先怀疑自己的选择器写错了（本产品历史上 7 列并排、
   `data-view` 取值都被误判过）。换几种选择器再试。
2. 三种情况**必须都在真实浏览器里跑**（jsdom 不做布局，量不出"看起来一片空白"）。
3. 断言前**等够时间**：本产品"输入 → 界面变"约需 1800ms。
   等 1000ms 就说"没反应"是**误判**——本产品在 Day 11 因此一天误判过 3 次。

## 输出格式

按这个格式给结论，别写成长篇评价：

```
情况① 有结果   ✅ / ❌   证据：<输入了什么> → <看到了什么>
情况② 无结果   ✅ / ❌   证据：...
情况③ 清空恢复 ✅ / ❌   证据：...
```

**每一项都必须带证据**（输入什么、看到什么），没有证据的项不算通过。

## 已知边界（不查）

- 搜索的**模糊匹配、拼音、首字母**能力 —— 属"搜得准"，是上限
- 搜索**性能**（大数据量下的耗时）—— 本产品数据量固定为演示规模
- **高亮**匹配片段 —— 加分项，非底线
