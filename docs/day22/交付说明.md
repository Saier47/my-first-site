## 3. 改了什么

### 3.1 数据访问层（`cloudfunctions/api-func/db.js`）

| 新增 | 干什么 |
|---|---|
| `update(name, id, patch)` | `PATCH /<表>?id=eq.xxx` + `Prefer: return=representation`；自动补 `updated_at`；丢掉 `id` / `created_at` |
| `remove(name, id)` | `DELETE /<表>?id=eq.xxx`；**靠"删到了几行"判断这条在不在** |

**🔑 为什么都不「先查再改/删」**：那样中间有并发窗口（查到了、写之前被别人删了）。
直接拿「**改到了 0 行 / 删到了 0 行**」当"这条不存在"，一次往返就够。

**`updated_at` 也是一个坑**：表里那一列只有 `DEFAULT now()`、**没有触发器**，
不显式写就永远停在创建时间 —— 那一列等于废了。

### 3.2 HTTP 层（`cloudfunctions/api-func/index.js`）

- 新增 `matchRoute()`：路由从**精确查表**升级成能认 `/api/courses/<id>` 这种带 id 的路径
- 新增 `handlePatch()` / `handleDelete()`
- **方法分发拆成两种路径**：

| 路径 | 允许的方法 |
|---|---|
| 集合 `/api/courses` · `/api/ddls` | `GET` · `POST` |
| 单条 `/api/courses/<id>` · `/api/ddls/<id>` | `PATCH` · `DELETE` |

- **405 的文案重写了**：原来硬写着「这个接口只支持 GET 和 POST」，
  加完 PATCH 之后那句话就成了假话。新文案会直接点出最常见的成因：
  > 「路径 /api/courses 只支持 GET（读全部）和 POST（新建）。
  >  要改或删某一条，请带上它的 id：/api/courses/<id>。你用的是 DELETE」

- 新增 `write.patchable` 字段白名单（哪些字段允许被 PATCH 改）
- `VERSION` 0.4.0 → **0.5.0**

### 3.3 🔑 `handlePatch` 里最需要想一下的地方：怎么复用 POST 的校验

直接拿 `patch` 去跑 `validateCourse` 会**误报「缺少必填字段 name」** ——
它要求字段全都在，而「我只想改个教室」的时候它们当然不在。
但完全不校验也不行 —— 「结束时间早于开始时间」这种**跨字段**规则是真正的业务规则。

**做法：把 patch 合并到「改完之后应该长什么样」，再整体校验。**

```
只传 location            → 合并后 name / 时间都在 → 不误报"缺字段"
传 end_time 早于 start_time → 合并后这条规则照样拦得住 ✅
```

这就是「PATCH 是局部替换」在代码里的样子。

> ⚠️ 唯一例外是 `done`：`validateDdl` 里那句「新建时固定 false」是 **POST 的规则**，
> 改 `done` 是 PATCH 的合法用法（勾选完成走的就是它），所以它从 patch 原样取。

## 5. 🔴 两个必须记下来的坑

### 5.1 「命令跑了 ≠ 命令生效了」——部署那次

第一次改完 `index.js` 部署，命令**退出码 0、但输出里没有 `deployed successfully`**。
我没当回事 → 结果**行为没变**（`done` 传非布尔值还是回 200）。
**是"再验一次行为"才发现的**，不是看工具输出发现的。
重跑部署、这次打印了 `✔ deployed successfully`，行为才对。

> 这个项目第 N 次踩同一个坑。**部署完不许凭工具输出下结论，必须验行为。**

### 5.2 我自己写出来的一个「假成功」（已修）

`done` 传 `"yes"` / `1` / `"true"` / `null` → 接口回 **200**，库里**静默写成 `false`**。
元凶是 `out.done = (patch.done === true)`。
**假成功比报错坏得多**：调用方以为设成了"已完成"，拿到的是个反的值，还不报错。
→ 改成：`done` 存在但非布尔 → **400 + 中文**「必须是 true 或 false」。
`check-day22.js` 的 B 组把它钉住了（含一条"被拦下后库里没被写坏"的断言）。

## 6. 顺手改掉的「会变成假话」的地方

接口一变，「哪些话不再成立」比代码更容易被忘掉。今天改了四处：

| 位置 | 原来（现在不成立了） | 现在 |
|---|---|---|
| `check-day18.js` | 「DELETE 到写接口 → 405（**本期不做删除**）」 | 「DELETE 打到**集合路径**（忘了带 id）→ 405」+ 新增"文案要点出 id"断言 |
| `check-day17.js` | 「PUT 到接口返回 405（Day 18 起 POST 已合法）」 | 「PUT 到集合路径返回 405（**PUT 至今哪个接口都不支持**）」 |
| `api-contract.md` 第 2.4 节 | 「对**只支持 GET / POST** 的接口发 PUT、DELETE」 | 写清**集合路径 / 单条路径**各认哪些方法 |
| `api-contract.md` 第 4 节 | #3 #4 #7 #8 状态是空的（第 16 天的占位） | 全部标 ✅ **Day 22 已实现** |
| `README.md` | 「⚠️ 编辑 / 删除**目前会报错**」 | 「✅ 已经能用了」+ 四类操作对照表 |

> 这就是项目里记过的老坑：**断言绑了实现细节** —— 代码改了，标签变成了假话。
> 好消息是那两条老断言**打的是集合路径，所以仍然通过**；
> 坏消息是**它通过了、标签却是骗人的** —— 那种"绿得没有任何信息量"的测试最危险。
