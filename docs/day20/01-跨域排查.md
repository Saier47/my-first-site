## 2. 🔴 关键发现：跨域已经通了，但不是我们写的

响应头里出现：

```
server: tcbgw
x-cloudbase-upstream-type: Tencent-SCF_HTTP
access-control-allow-origin: https://my-first-site-d0g3re4p71560e327-1500310885.tcloudbaseapp.com
access-control-allow-credentials: true
```

`server: tcbgw` = **腾讯云网关**。它在转发前后**自己补上了跨域头**，
函数代码 `index.js` / `api-health/index.js` 里**一行 CORS 代码都没有**
（已 grep 确认）。

### 为什么决定「不手动再加」

网关返回的是**精确回显这次请求的 `Origin`**。如果函数里再写一份
`Access-Control-Allow-Origin: *`，浏览器会收到**两个**该头 ——
按 CORS 规范属于**无效响应**，反而把已经通的跨域弄坏。

→ 所以板块 ① **不改任何后端代码**，只留本文件作为证据。

## 3. 🔑 今天要掌握的那句话（答案）

> **跨域被拦时，请求其实已经打到服务器了。**
> 浏览器是看到响应里缺 `Access-Control-Allow-Origin` 才把结果掐掉的。

**怎么认出问题出在哪 —— 看后端日志：**

| 后端日志 | 结论 |
|---|---|
| **有**这次请求（有 requestId） | **跨域问题** → 查/补响应头 |
| **没有**这次请求 | 根本不是跨域 → 请求没发出去（网络/网址写错/前端没调） |

### 同一类盲区（Day 15 那条的兄弟）

`curl` **不检查跨域**（跨域是浏览器的规矩，不是 HTTP 的规矩）。
所以 curl 全绿 ≠ 浏览器里能跑 —— 这跟 Day 15「curl 测不出警告页」是同一种坑：

> **工具没报错，不代表用户看到的是对的。换一个角度再验一遍。**

→ 所以板块 ④ 必须用**真浏览器**验收，不能只靠 curl。
