## 一、今天要掌握的那个问题

> **你把哪句裸报错改成了人话？改前改后分别是什么？**

改的是 **4 句**，都属第 ③ 类（服务器自己的问题）：

| 改前（裸报错） | 改后（人话） |
|---|---|
| `数据库暂时读不到数据，请稍后再试` | `我们这边出了点问题：数据库暂时读不到数据。不是你操作的问题，过一会儿再试一次就行。` |
| `数据库暂时写不进去 / 改不了 / 删不了，请稍后再试` | `我们这边出了点问题：数据库暂时<写不进去>。不是你操作的问题，过一会儿再试一次就行。` |
| `服务内部出错了，请稍后再试` | `我们这边出了点问题：处理这次请求时出错了。这不是你操作的问题，过一会儿再试一次；如果一直这样，把这串编号发给管理员：req_xxxxx` |
| `服务端没有配置数据库密钥，请联系管理员检查云函数环境变量` | `我们这边出了点问题：服务端还没配好数据库密钥。这不是你操作的问题，已经记下来了，稍后会自动恢复；如果一直这样，把下面这串编号发给管理员：req_xxxxx` |

**"裸"在哪 → 变成了什么：**

| 问题 | 说明 |
|---|---|
| 没说**这是谁的锅** | 用户看到"数据库读不到数据"，会以为是自己填错了 → 加"**不是你操作的问题**" |
| 说了**开发者才懂的词** | "服务内部出错""环境变量"是说给我自己听的 → 换成用户视角的话 |
| **没给请求编号** | 用户报故障说不清是哪一次 → 500 的提示里带上 `requestId` |
| 没给**量级参照**（413） | "太大了"没说正常多大 → "课表一条记录最多几百字节" |

### 2.2 🔑 关键动作：先证明"尺子"是准的

**「扫出 0 条」有两种可能，输出一模一样：**

1. 仓库真干净
2. 扫描器坏了，什么都扫不到

所以**第一步不是扫描，是自检** —— 造 8 类假密钥样本，看扫描器能不能全扫出来。

**结果：8 条规则里，第一次跑就发现 3 条是坏的。**

| 漏掉的规则 | 原因 |
|---|---|
| OpenAI `sk-` | 正则写 `[A-Za-z0-9]`，真实 Key 是 `sk-proj-…`，被**连字符截断** |
| 赋值式 `password` | 用了 `\b` 词边界，而 `_` 算单词字符 → `db_password` **匹配不上** |
| CloudBase 环境密钥字段 | 负向先行写错，把正常值一起拦了 |

**修好后自检 9/9 全过。** 这一步的价值：**没有它，那个"0 条"就是假的安全感。**

### 2.3 三个独立角度，全部 0 命中

| 角度 | 方法 | 结果 |
|---|---|---|
| 工作区文件 | `audit-secrets.py`，8 类规则 | **0 条** ✅ |
| git 全历史 | `git log --all -p` 逐行扫（含已删除行） | **0 条** ✅ |
| **GitHub 远端真实内容** | `origin/main` 树 + `cat-file` 逐文件拉，64 个文本文件 | **0 条** ✅ |

> **为什么必须扫 git 全历史**：密钥提交过、后来又删掉 ——
> 当前快照是干净的，但 `git log -p` 里还留着，推到 GitHub 就永久留痕。
> **只扫工作区的检查会给出假的安全感。**

> **远端 111 个文件里唯一点到 "secret" 的是** `scripts/check-no-secrets.sh` ——
> **检查脚本自己**，本来就该提交。没有任何 `.env` / `apikey.txt` / `.secrets`。

> ⚠️ **远端这条是怎么验的（如实交代）**：本来想 `git clone --depth 1` 一把梭，
> 但**大陆网络下 clone 超时**；改走 GitHub API 又超时。
> 最后用 `git cat-file -p origin/main:<路径>` 逐个读 ——
> **那是远端树里的真实内容**（本地对象库里同步下来的远端快照），
> 一样是"别人 clone 我的仓库能拿到的东西"。
>
> 🔑 **一次失败的操作 ≠ "没问题"**。clone 超时不能算作"检查通过"，
> 所以换了一条能真跑通的路，而不是把失败当默认干净。
> （当时还写了个 `scan-remote.py` 走 GitHub API，但它一次都没跑成 ——
>  **没验证过的工具不进仓库**，已删。）

## 三、板块② .env 与忽略规则检查

### 3.1 发现的真缺口

`scripts/check-no-secrets.sh` 原来只有 **3 项**检查：

1. `cloudbaserc.json` 是不是占位符
2. 仓库里有没有 JWT 形状的串
3. `.secrets/` 被忽略了吗

**但它从来没验过 `.env` 本身。**

> 🔴 **`.gitignore` 里写了 `.env`、和 `.env` 实际有没有被 git 跟踪，是两件事。**
> 如果曾经 `git add -f` 强加过一次，`.gitignore` 就形同虚设，之后每次提交都跟着走。
> 这正是项目的铁律：**「文件里写了」≠「真的生效」。**

### 3.2 补上两项检查（3 项 → 5 项）

| # | 检查项 | 状态 |
|---|---|---|
| 1 | `cloudbaserc.json` 是占位符而非真 Key | ✅ 原有 |
| 2 | 全仓库无 JWT 形状字符串 | ✅ 原有（Day 23 加白名单**修误报**） |
| 3 | `.secrets/` 被忽略 | ✅ 原有 |
| 4 | **`.env` / apikey / `.secrets` 未被 git 跟踪** | ✅ **Day 23 新增** |
| 5 | **`.env` 存在且命中忽略规则** | ✅ **Day 23 新增** |

**5 项全绿**（第 4、5 项是互补的：一个防"已发生的事"，一个防"未发生的事"）。

### 3.3 顺手修的误报

原来的 JWT 检查**会误报** —— 它只认形状不看上下文。
Day 23 写扫描器的自检样本时就撞上了：含假样本的文件被报成"发现 JWT"（其实全是编的）。

**修法**：加白名单放行占位符与文档式示例，并把 `audit-secrets.py` 自己也跳过
（免得"检查工具被自己检查"）。

## 四、板块③ 三类错误提示统一

### 4.1 分类标准：按「用户该做什么」分，不是按状态码分

| 类 | 状态码 | 用户该做什么 | 文案句式 |
|---|---|---|---|
| **① 你的输入要改** | 400 / 409 / 413 | 改一下内容再发 | `<哪里>不对：<为什么>。应该<怎么改>，比如「<例子>」` |
| **② 它不在了 / 没这地址** | 404 / 405 | 刷新或换个地址/方法 | `没有找到<什么>，<可能的原因>` |
| **③ 我们这边的问题** | 500 / 502 | **等一会儿重试，别改输入** | `<环节>出了问题。不是你操作的问题，过一会儿再试一次就行。` |

### 4.2 具体改了什么

| 位置 | 改动 |
|---|---|
| `index.js` 新增说明块 | 把三类定义 + 三条硬规矩写进代码，后来人改提示不用猜 |
| 新增 `ourFault()` 拼装函数 | 7 处 502 的"不是你的错"抽成常量 → **改一次全生效**，不会漏 |
| 7 处 502 | 全部改用 `ourFault(...)` |
| 1 处 500（未捕获） | 加"不是你的错" + **带上 requestId** |
| 1 处 500（密钥没配） | 去掉"环境变量"这类运维词 + 带上 requestId |
| 2 处 413 | 加量级参照（几百字节 vs 64KB）+ 最可能的原因 |
| 版本号 | `0.5.0` → `0.6.0` |

### 4.3 为什么抽成常量

这 7 条 502 的**共同部分**才是最重要的那句 —— 「不是你的错」。
散着写，早晚有一条忘了带，而用户正好撞上那一条。放一处，改一次全生效。

### 4.4 没动的部分（统一 ≠ 全部重写）

第 ② 类的 404 / 405 **已经满足标准**，保持原样：

- 404：`没有找到 id 为「xxx」的记录，可能已经被删掉了`（回显 id + 给解释）
- 405：`路径 /api/courses 只支持 GET…和 POST…。要改或删某一条，请带上它的 id：/api/courses/<id>。你用的是 PUT`（说清支持什么 + 该打哪 + 你用了什么）

**把已经合格的东西再改一遍，只会引入新风险。**

## 五、验证（两个脚本，共 61 项）

| 脚本 | 项数 | 结果 |
|---|---|---|
| `check-day23.js`（静态层 + 联网层） | 50 | **50/50 ✅** |
| `check-day23.sh`（bash 层：真实子进程） | 11 | **11/11 ✅** |
| **合计** | **61** | **全绿** |

**为什么拆成两个脚本（这是个真教训）：**

> `check-day23.js` 一开始把「真跑一遍自查脚本」也写进去了，
> 结果 D1/E1 报**失败**。我第一反应是"脚本坏了" ——
> 其实报错是 `EBUSY`：**本沙箱禁止 Node 派生任何子进程**（连 node→node 都不行）。
>
> **它不是"跑出来是坏的"，是"根本跑不动"** —— 两者从断言上看一模一样。
> 分不清的时候先问一句：是**被测对象**不对，还是**我这把尺子**量不了？
>
> 修法：那两组搬进 `check-day23.sh`（bash 起子进程是正常的）。

**联网层真打线上接口验的东西：**

- H 组（第 ① 类）：缺字段、超范围、坏 JSON → 全 400，提示是中文、有"比如"、无技术词
- I 组（第 ②③ 类）：404 回显 id、405 点出"带上 id"、路径不存在 404
- I11 ★ 第 ③ 类**必须**出现"不是"二字（这条能写成断言，就说明它是真规矩）
