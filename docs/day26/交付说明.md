## 一、今天要掌握的那个问题

> **回滚演练花了多久？真出事你敢不敢用这套流程？**

### 花了多久

| 阶段 | 耗时 |
|---|---|
| 导出 + 校验 8 个文件 | ~9 秒 |
| **上传（`tcb hosting deploy`）** | **4 秒** |
| CDN 生效（实测） | **几乎立刻** |
| **整条链路（不含人的思考）** | **约 15 秒** |

### 敢不敢用

**敢。** 理由不是"流程很顺"，而是：

1. **十几秒**的代价，远小于"让用户对着白屏等半小时"
2. 脚本每步都有校验：目标版本不存在不传、8 个文件缺一个不传
3. **回滚完能立刻验证**（`preflight` 第【4】项会告诉你"线上已经是旧版了"）

**但有一个前提不敢打包票**：**"上一版真的是好的吗"** —— 回滚到一个你以为没问题、其实也有问题的版本，是最坏的情况。
所以配套纪律是：**每次发布前跑 `preflight.sh` 到 8/8**。

**最大的窟窿不是回滚，是数据** —— 见 `回滚手册.md` 第四节。

## 二、四板块

### ① 确认可回退历史

**发现**：项目里**一个 tag 都没有** —— "v1.0"只是个说法，不是能指认的坐标。

**做的事**：
- `package.json` + 云函数 `VERSION` 升到 **1.0.0**
- 打 **`git tag v1.0.0`**（annotated，带说明）并推到远端
- 页面上显示版本徽标 → 从此"用户看的是哪个版本"能一眼报出来

> 中间有一次第【8】项红（"有提交没推上去"）—— **那是检查在正常工作**，推完就绿了。

### ③ 静态托管回退演练 ⭐

**核心认知**：**CloudBase 静态托管没有版本管理**。

```
tcb hosting deploy 的帮助原文：
Upload static files to cloud storage (file upload only, no build, no version management)
```

对比云函数：`publish-version` / `list-function-versions` / `config-route`（切流量）**静态托管一个都没有**。
**所以回滚 = 拿旧 commit 的文件重新传一遍，没有"点一下回去"的安全网。**

**演练过程（目标 `ef2fa36`）**：

| 阶段 | 结果 |
|---|---|
| dry-run（先看会变什么） | `index.html` +18 / -1 行 |
| 上传 | **4 秒** |
| 线上 `class="ver"` 徽标 | **消失** ✅ |
| 线上 `index.html` 字节 | 44445 → **43879**（回到 v1.0 之前）✅ |
| `preflight` 第【4】项 | **❌ 报不一致** ← 铁证 |

> 💡 **第【4】项报红不是 bug**：本地是 v1.0、线上是旧版，"不一致"恰好说明**回滚真的发生了**。
> Day 25 做的那个检查，今天正好用来给回滚作证。

## 三、一个必须说的"设计性发现"

**dry-run 救了一次**：

第一次跑 `rollback-web.sh ef2fa36 --dry-run`，输出是：

> （这 8 个部署文件一个都没变 —— 回滚不会改变线上内容）

因为 Day 25 只改了文档和脚本，**没碰前端**。也就是说：**回滚到那个版本，线上什么都不会变**，
演练会"看起来像没生效"，白折腾一场。

**处理**：给 v1.0 加了**页面版本徽标** —— 既是有用的（用户能报版本），也让回滚有了肉眼可见的差异。

> 🔑 **这条值得记住**：**演练前先 dry-run**。
> 不做这一步，你会花 10 分钟做完回滚，然后对着"看不出变化"的页面怀疑是不是脚本坏了。
