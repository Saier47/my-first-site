## 一、先分清：是"代码坏了"还是"数据坏了"

**这是最容易搞错、代价最大的一步。**

| 你看到的现象 | 真正的问题 | 该做什么 |
|---|---|---|
| 页面白屏 / 打不开 / JS 报错 | **代码坏了** | ✅ **回滚前端** |
| 点了保存没反应、删除失败、勾选不生效 | **代码坏了** | ✅ **回滚前端** |
| 数据值错了、乱码、多了重复记录 | **数据坏了** | ❌ **回滚没用** —— 回滚只会让"能用的代码 + 坏数据"变成"旧代码 + 坏数据" |
| 接口 502 / 超时 | 可能是数据库或云函数 | ⚠️ 先看云函数日志，**别急着回前端** |
| 只有你这台电脑上不对 | 大概率是缓存 | ❌ 先强制刷新 / 换浏览器试 |

> 🔑 **回滚只能退"代码"，退不了"数据"。**
> 数据坏了要去修数据（改库 / 从备份恢复），那是另一套流程 —— 见本文第四节的未完成部分。

## 二、什么情况必须回滚（判断表）

| 情况 | 回不回滚 | 理由 |
|---|---|---|
| **页面完全打不开 / 白屏** | 🔴 **立即回滚，别犹豫** | 用户 100% 用不了，多等一分钟都是损失 |
| **核心功能断了**（存不了课、删不了 DDL、勾选不生效） | 🔴 **回滚** | 这是产品存在的理由，断了就等于没有 |
| **错误提示全是乱码 / 显示 `undefined`** | 🟠 看情况 | 功能还在，但用户会怀疑产品坏了 —— 影响小可以等修 |
| 某个次要按钮失效（如"编辑"点不动） | 🟡 先评估 | 有替代路径（删了重建）就可以等修，没有就回滚 |
| **只是样式丑了 / 颜色不对 / 排版错位** | 🟢 **不回滚** | 能用就别动。回滚的风险 > 丑一会儿的代价 |
| **数据被写坏了**（值错、重复、丢失） | 🟢 **不回滚** | 回滚修不了数据，只会让问题更难查 |
| 只有你的电脑上出问题 | 🟢 **不回滚** | 先怀疑缓存 / 网络 / 浏览器 |
| 刚部署完就出问题 | 🔴 **立刻回滚**，然后再查 | 先止血，后复盘。**"边查边让用户等着"是最差的选择** |

**一条总原则**：

> **回滚是为了"先让用户能用"，不是为了"把问题修好"。**
> 所以判断标准只有一个：**现在的线上，用户还能不能完成他本来要干的事？**
> 不能 → 回滚。能 → 别动，去修。

## 三、静态托管回滚（**唯一能实操的路径**）

### 3.1 为什么没有"一键回滚"

CloudBase 静态托管**没有版本管理**。`tcb hosting deploy` 的帮助原文：

```
Upload static files to cloud storage (file upload only, no build, no version management)
```

云函数那套 `publish-version` / `list-function-versions` / `config-route`（切流量）**在静态托管上一个都没有**。

**所以回滚 = 拿旧版本的文件重新传一遍。没有安全网。**

### 3.2 操作（一条命令）

```bash
cd my-first-site

# 1) 先看会变什么，不真传
bash scripts/rollback-web.sh ef2fa36 --dry-run

# 2) 确认无误再传
bash scripts/rollback-web.sh ef2fa36 --yes
```

脚本会做这几件事：

1. 用 `git rev-parse` 确认目标版本**真的存在**
2. `git diff --stat` 列出**这次会改哪几个文件**
3. `git archive` 从目标版本导出 8 个部署文件，**逐个校验存在**（缺一个就停下，不传半套）
4. 计时上传
5. 打印下一步该验什么

### 3.3 回滚之后必须验证（别只看命令行说成功）

```bash
bash scripts/preflight.sh
```

**第【4】项会报「线上和本地不一致」—— 这不是 bug，是回滚成功的铁证**（线上是旧版、本地是最新版）。

如果第 4 项**反而绿了**，说明回滚没生效（可能 CDN 还没刷，等 1–2 分钟再跑）。

### 3.4 实测耗时（2026-10-18 演练）

| 阶段 | 耗时 |
|---|---|
| 从 `git archive` 导出 + 校验 8 个文件 | ~9 秒 |
| **上传（`tcb hosting deploy`）** | **4 秒** |
| CDN 生效（实测） | **几乎立刻**（没等到"几分钟"） |
| **整条链路（不含人的思考时间）** | **约 15 秒** |

> 这个数字是今天敢用这套流程的底气：**十几秒能退回去**。
> 真出事时，这个代价远小于"让用户对着白屏等半小时"。

### 3.5 恢复（回到最新版）

```bash
# 方式一：重新部署当前 HEAD 的 8 个文件
rm -rf .deploy-tmp && mkdir -p .deploy-tmp
cp index.html app.js store.js mock-data.js manifest.json \
   apple-touch-icon.png icon-192.png icon-512.png .deploy-tmp/
tcb hosting deploy .deploy-tmp -e my-first-site-d0g3re4p71560e327

# 方式二：如果脚本允许（目标 = 当前 HEAD）
bash scripts/rollback-web.sh HEAD --force
```

**恢复后同样要跑 `preflight.sh` 到 8/8 全绿**，别只看部署命令的输出。

## 四、云函数回退（**只备查，本期未实操**）

> 今天清单明确"不做云函数回退实操"。下面这些命令**没有在本项目里真跑过**，
> 真要用之前**先在测试环境验证一遍**。

云函数**有**版本管理，这是它比静态托管强的地方：

```bash
# 1) 把当前代码发布成一个版本（回滚的前提是"旧版本被发布过"）
tcb fn publish-version api-func "v1.0.0"

# 2) 看有哪些版本
tcb fn list-function-versions api-func

# 3) 把流量切回旧版本（比如 100% 到版本 2）
tcb fn config-route api-func 2 1
```

**⚠️ 两个坑（推测，未验证）**：
- **`publish-version` 要提前做** —— 出事时才想"发布个版本"，发布的是**当前这份坏的**。
  所以正常发布流程里就该带上 `publish-version`。
- 切流量后**旧版本用的是旧的环境变量**，如果这期间改过配置，行为可能和预期不同。

## 七、敢不敢用？—— 演练后的真实回答

| 问题 | 回答 |
|---|---|
| 流程敢不敢用 | ✅ **敢**。十几秒，一条命令，每一步都有校验 |
| 最大的不确定性是什么 | **"上一版真的是好的吗"** —— 回滚到你以为没问题、其实也有问题的版本，是最坏的情况 |
| 怎么消除它 | 每次发布前跑 `preflight.sh` 到 8/8；**发布后立刻在公网验一遍再走开** |
| 最怕出什么 | **数据坏了**（回滚救不了，而且现在没有备份） |

> 所以真正该补的不是"回滚更快"，而是**备份**。
> 回滚练得再熟，数据丢了也回不来。
