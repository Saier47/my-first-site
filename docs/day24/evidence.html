1怎么复现的（诚实说明）

真实用户场景是信号差（地铁、电梯）：请求发不出去。自动化里没法拔网线， 所以用等价手段：把 DELETE 请求改成必定失败，GET 保持正常 —— 这样"点击 → 确认 → 删除请求失败"整条链路跟真实断网一模一样。

// 注入到页面里（模拟"删到一半网断了"） var orig = window.fetch; window.fetch = function (url, opts) { if (opts && opts.method === 'DELETE') { return Promise.reject(new TypeError('Failed to fetch')); // 断网时浏览器给的就是这个 } return orig.apply(this, arguments); };

2🔴 修复前 · 控制台报错原文

Console — 点删除、确认后 
[error] [store] 请求发不出去 /api/courses/c_seed_01 {stack: "TypeError: Failed to fetch    at window.fetch (…/app.js:857:27)", message: "Failed to fetch"}（然后就没了 —— 这句话之后，再没有任何一层接住这个错误）
为什么异常会"冒出去"：store 层把 fetch 的失败包成一个中文 Error 往上抛 （"连不上服务器，请检查网络后重试"）， 而 removeRecord() 和它的调用方都没接 —— 于是它成了 未捕获的 Promise 拒绝。用监听器把这件事抓了个现行：
window.__unhandled = ["连不上服务器，请检查网络后重试"] ← 非空 = 有一个异常没人管
F12 里这一行会显示成 Uncaught (in promise) Error: 连不上服务器，请检查网络后重试 —— 普通用户永远看不到它，也不会去看。

3🔴 修复前 · 界面上发生了什么

document.querySelectorAll('.state-error').length = 0 ← 一个错误提示块都没有 #toast 的 opacity = 0 ← 提示条没显示 "高等数学" 还在列表里吗 = 是 ← 删除确实失败了

三者合起来就是问题：操作失败了（记录还在）、但界面没有任何反馈、 而且用户也无从知道 —— 他只会以为"我刚才点偏了"。

4定位 · 差在哪一行

从报错堆栈往回追到 onClick（事件总入口），一见分晓：

// app.js 的 onClick（事件委托总入口） } else if (action === 'edit') { openEdit(kind, id); // ← 异步函数，异常没人接 } else if (action === 'delete') { removeRecord(kind, id); // ← 一样 } else if (action === 'retry') { render().catch(function (err) { … }); // ← 这个记得接 }
成因说明
Day 20 写这三个函数时 数据来自 localStorage —— 读本地几乎不会失败，所以没人想到要处理失败
Day 22 换成云接口后 "请求可能失败"这条路才第一次真的存在，但这三个调用点没跟着补 catch
一条通用教训：把"不会失败的代码"换成"会失败的代码"时， 最容易漏掉的就是失败这条路 —— 它平时不显形，只在对应用户身上显形。

另一个场景：勾选「已完成」失败（更隐蔽）

这个比删除更阴险 —— 因为复选框在浏览器里已经变成勾上了， 界面看上去像"操作成功了"，其实数据根本没存上。

初始 checked = true ← 这条 DDL 本来就是"已完成" 点一下之后 checked = false ← 浏览器先切了（它不管请求成不成） 3 秒后 checked = true ← ✅ 被拨回来了 提示条 = "勾选没成功：连不上服务器，请检查网络后重试" 未捕获异常 = []
为什么一定要拨回去：不拨的话，界面显示"已完成"、库里还是"未完成" —— 用户一刷新就自相矛盾，而且他永远不知道哪一次才是真的。 这类"界面撒谎"跟 Day 22 修的「done 被静默写成 false」是同一种病。

6修复了什么（三处 + 一个额外）

// 1) 统一的"失败了要说话" async function reportActionFailure(whatFailed, err) { const why = (err && err.message) ? err.message : '未知错误'; console.error('[app] ' + whatFailed + '失败：', err); // 开发者看全的堆栈 showToast(whatFailed + '没成功：' + why, 'error'); // 用户看一句人话 } // 2) 三个函数各自 try/catch —— 函数自己保证不漏异常， // 比指望每个调用点都记得加 catch 靠谱 async function openEdit(...) { try { … } catch (err) { await reportActionFailure('打开编辑', err); } } async function removeRecord(...) { try { … } catch (err) { await reportActionFailure('删除', err); } } async function toggleDone(...) { try { … } catch (err) { restoreCheckbox(id, !checked); await reportActionFailure('勾选', err); } }
额外处理为什么
勾选失败要拨回复选框 change 事件触发时浏览器已经把框切到新状态了。请求失败 = 数据没存上 —— 不拨回去界面就在撒谎：显示"已完成"，一刷新又变回未完成
记录不存在时也要说一声 原来 if (!target) return; 是静默返回 —— 用户点了「编辑 / 删除」却什么都没发生，跟刚修的 Bug 是同一类毛病
