## 一、今天要掌握的那个问题

> **你是怎么排除掉其他原因、锁定真正原因的？**

**排查的顺序是这样的**（先列可能，再逐个排除）：

| # | 假设 | 怎么排除 | 结论 |
|---|---|---|---|
| 1 | 按钮根本没绑上事件？ | 点它 → **确认框正常弹出**（「确定删除「高等数学」吗？」） | ❌ 事件是通的 |
| 2 | 请求压根没发出去？ | 控制台有 `[store] 请求发不出去 /api/courses/c_seed_01` | ❌ 发出去了，是**失败**了 |
| 3 | 后端把请求拒了？ | 报错是 `TypeError: Failed to fetch` —— **请求还没到服务器**就断了 | ❌ 不是后端的事 |
| 4 | 请求失败了，但前端没接住？ | 装 `unhandledrejection` 监听器 → 抓到 `["连不上服务器，请检查网络后重试"]` | ✅ **就是它** |
| 5 | 只有「删除」这样吗？ | 试了「编辑」「勾选」，三个一模一样 | ✅ **是一类问题，不是单点** |

**最后一步是关键**：前 3 个假设都是"排除法"——每一步都真做了一次，而不是靠读代码猜。
第 4 步的那个监听器，是我**为了让它自己招供**专门装的：

```js
window.__unhandled = [];
window.addEventListener('unhandledrejection', function (e) {
  window.__unhandled.push(String((e.reason && e.reason.message) || e.reason));
});
```

> 🔑 **为什么不是"一上来就读代码找"**：
> 读代码能找到"哪里可能错"，但**不能证明"错的就是它"**。
> 先让现象自己说话（哪个环节断的），再去代码里找对应的地方 ——
> 这样找到的那一行才有分量。

## 二、Bug 是什么

**「编辑 / 删除 / 勾选完成」这三个操作失败时，界面一个字都不说。**

| 操作失败时…… | 修复前 |
|---|---|
| 界面上 | **什么都没发生** —— 记录还在、没提示、没报错 |
| 控制台 | 一条 **未捕获的** Promise 拒绝 |
| 用户感受到的 | "我刚才是不是点偏了？" → 再点一次 → 还是没有 |

**最阴险的是「勾选完成」**：复选框在浏览器里**已经**变成勾上了（`change` 事件先发生），
但数据没存上 —— **界面在撒谎**，用户一刷新就发现"白勾了"。

### 根因（这才是重点）

```js
// app.js 的 onClick（事件委托总入口）
} else if (action === 'edit') {
  openEdit(kind, id);          // ← async 函数，异常没人接
} else if (action === 'delete') {
  removeRecord(kind, id);      // ← 一样
} else if (action === 'retry') {
  render().catch(...);         // ← 这个记得接
}
```

**同一段代码里，`render()` 接了异常，那三个没接** —— 说明这是**漏**，不是设计。

| 时间 | 发生了什么 |
|---|---|
| **Day 20** | 写这三个函数时，数据来自 `localStorage` —— **读本地几乎不会失败**，所以没人想到要处理失败 |
| **Day 22** | `store.js` 内部换成调云接口 —— **"请求可能失败"这条路才第一次真的存在**，但这三个调用点没跟着补 |

> 🔑 **通用教训：把"不会失败的代码"换成"会失败的代码"时，最容易漏掉的就是失败那条路。**
> 它平时不显形 —— 只在对应用户身上显形（地铁里、电梯里、信号差的时候）。

## 三、修复了什么

| # | 改动 | 为什么这么做 |
|---|---|---|
| 1 | 新增 `reportActionFailure(whatFailed, err)` | 统一"失败了要说话"：完整堆栈进 console（给开发），一句人话进提示条（给用户） |
| 2 | `showToast(text, kind)` 支持 `'error'` | 失败提示必须是红的 + 图标换 `!`，否则用户会把"失败"看成"成功" |
| 3 | **三个函数各自加 `try/catch`** | **函数自己保证不漏异常，比指望每个调用点都记得加 catch 靠谱得多** |
| 4 | `toggleDone` 失败时 `restoreCheckbox(id, !checked)` | change 事件已把框切了，不拨回来界面就在撒谎 |
| 5 | 记录不存在时也提示（原来 `if (!target) return;` 静默） | 同一类毛病：用户点了没反应 |
| 6 | `index.html` 加 `--danger` 变量 + `.toast.is-error` 样式 | 失败态配色独立，别跟 DDL 的语义色混用 |

### 为什么错误文案直接能用

`store.js` 抛出的 `Error.message` **本来就是中文**（Day 23 定的规矩）：
- 断网 → `连不上服务器，请检查网络后重试`
- 后端拒绝 → 后端那句 message

**所以前端只要把 `err.message` 显示出来就是人话。**

> 📌 **今天这个修复，才让 Day 23 的成果真正落到用户眼前** ——
> Day 23 把后端文案改好了，但前端不接异常，用户一个字也看不到。

## 四、验证（四步证据齐全）

### 4.1 复现（真浏览器 + 真断网场景）

自动化里没法拔网线，用等价手段：**把 DELETE / PATCH 请求改成必定失败，GET 保持正常** ——
这样"点击 → 确认 → 请求失败"整条链路跟真实断网一模一样。

```js
var orig = window.fetch;
window.fetch = function (url, opts) {
  if (opts && opts.method === 'DELETE') {
    return Promise.reject(new TypeError('Failed to fetch'));   // 断网时浏览器给的就是这个
  }
  return orig.apply(this, arguments);
};
```

**修复前的实测：**

| 测量项 | 结果 |
|---|---|
| 控制台 | `[error] [store] 请求发不出去 /api/courses/c_seed_01` + `TypeError: Failed to fetch` |
| `window.__unhandled` | `["连不上服务器，请检查网络后重试"]` ← **非空 = 有异常没人管** |
| `.state-error` 数量 | **0**（一个错误提示块都没有） |
| `#toast` 的 opacity | **0**（提示条没显示） |
| 记录还在吗 | **还在**（删除确实失败了） |

### 4.2 定位

从报错堆栈往回追 → `app.js:857` 正是 `await S.deleteCourse(id)` 那一行 →
再往上是 `removeRecord`（没接）→ 再往上是 `onClick`（没接）→ 落到 `window`。
**旁边 `render()` 那个 `.catch()` 就是对照组。**

### 4.3 修复后（同样操作、同样断网）

| 测量项 | 修复前 | 修复后 |
|---|---|---|
| 未捕获的 Promise 拒绝 | **1 条** | **0 条** |
| 控制台里有"有人接住"的痕迹 | 没有 | ✅ `[error] [app] 删除失败： {…}` |
| 界面反馈 | 完全沉默 | ✅ 红色提示条 |
| 提示条文案 | — | ✅ `删除没成功：连不上服务器，请检查网络后重试` |

**勾选那条路（最隐蔽的）也单独验了：**

```
初始        checked = true      ← 这条 DDL 本来就是"已完成"
点一下之后  checked = false     ← 浏览器先切了（它不管请求成不成）
3 秒后      checked = true      ← ✅ 被拨回来了
提示条      「勾选没成功：连不上服务器，请检查网络后重试」
未捕获异常  []
```
